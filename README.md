# Research Graph · 多智能体深度调研报告生成器

输入一个主题，多个 agent 并行检索、交叉核查、带引用成稿；大纲先人工确认。基于 LangGraph 的 StateGraph / 条件边 / interrupt / Send 并行 / Checkpointer。

## 图结构

```
planner → human_review（interrupt 人工确认大纲）
        → research_one_node × N（Send 并行，每路一个子问题）
        → fact_checker_node（代码找冲突/孤证候选，模型逐条确认）
        → writer（按大纲成稿，事实句标 [n]）
        → audit（接地检查：句子里的数字是否在被引笔记里）
        → critic（代码判硬指标 + 模型给建议）
           ├─ 硬问题 → revise → audit（最多 2 轮）
           └─ 达标 / 预算耗尽 → code_clean（补引用/删句/标推断）
                                → claim_verify（断言级核验，只记录不阻塞）
                                → END
```

## 跑起来

```powershell
cd research-graph
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env    # 填 DASHSCOPE_API_KEY 与代理端口
python server.py          # 浏览器打开 http://127.0.0.1:8000
```

命令行跑一次完整流程（自动放行大纲），产出三个文件：

```powershell
python run_cli.py "端侧 AI 芯片格局（2025-2026）"
# demo_report.md   报告
# demo_state.json  运行快照（笔记、冲突、审稿意见、指标）
# 控制台            指标 + 交付判定
```

离线测试（不联网、不花 API）：

```powershell
pip install pytest
python -m pytest
```

引用审计（逐句核对「句子里的数字/型号是否真的在被引来源里」）：

```powershell
python verify_report.py demo_report.md demo_state.json --fetch
# 退出码 0 = 全部可溯源；生成 verification.md
```

批量回归（多个主题各跑一次，汇总指标；`--resume` 只补跑失败的）：

```powershell
python batch_eval.py                              # 内置 5 个主题
python batch_eval.py topics.txt --resume          # 每行一个主题
# batch_results.json 明细，batch_report.md 汇总表
```

对比两次运行（来源是否漂移、指标变化、是否新增悬空引用）：

```powershell
python compare_runs.py demo_state_prev.json demo_state.json
```

校准断言核验（人工标注 claim-source 对，输出一致率与混淆矩阵）：

```powershell
python calibrate_claim_verify.py
# eval/claim_labels.example.jsonl 是示例标注；一致率 < 0.8 不要用于硬判
```

从真实报告导出待标注的 claim-source 对：

```powershell
python make_claim_labels.py demo_state.json
# 生成 claim_labels.to_label.jsonl，填好 label 后用它跑 calibrate
```

Web 端每次运行会落 `runs/`，首页右上角「历史」可看列表和详情：
来源层级、是否多源印证、每句引用、断言核验结果；运行中可点「取消」。

## 评测口径

| 指标 | 定义 | 目标 |
|---|---|---|
| 引用覆盖率 | 含数字/英文专名的事实句里带 [n] 的比例（切句含分号，标注「推断」「未披露」「待补充」的句子不计入分母） | ≥ 90% |
| 来源多样性 | 来源表中的唯一域名数 / 唯一页面数 | ≥ 3 |
| 冲突处理率 | fact_checker 标出的冲突在终稿（含代码生成的《数据分歧说明》）被说明的比例；未检出冲突时记为「未验证」而非 100% | 100% |
| 悬空引用 | 正文引用编号在来源表里找不到的个数 | 0 |
| 事实句数 | 参与覆盖率计算的分母；太少时覆盖率不具统计意义 | ≥ 12 |
| 初稿覆盖率 | `code_clean` 之前的口径，衡量模型本身写得怎么样 | 观察项 |
| 来源质量 | 官方/机构、媒体、自媒体、未知四档分布 + 多源印证条数 | 观察项 |
| 断言核验 | 带引用的高风险句子中 supported / partial / unsupported 的分布 | 观察项（校准 ≥0.8 才可硬判） |
| Token | 按节点统计的 input/output tokens 与调用次数 | 观察项 |
| 返工次数 | critic 触发 revise 的次数 | 观察项 |

`targets_met` 要求全部达标（冲突必须真实检出并处理）；`quality_ok` 是可交付判定，
允许「冲突未检出」，但要求覆盖率、悬空引用、事实句数下限都达标且无阻塞性硬问题。

覆盖率是**交付前兜底之后**的口径：补引用、删句、标推断都会改变分母，
所以单看 100% 没有意义。批量报告会同时给出三类兜底的触发次数：

| 主题 | 字数 | 初稿→终稿覆盖率 | 来源(域名/页面) | 冲突 | 悬空 | 补引用/删句/标推断 | 断言核验 S/P/U | 耗时 |
|---|---|---|---|---|---|---|---|---|
| 端侧 AI 芯片格局（2025-2026） | 2639 | 1.000→1.000 | 3/3 | 4 | 0 | 0/1/0 | 2/0/6 | 278s |
| RISC-V 在数据中心服务器的落地进展 | 3509 | 0.917→1.000 | 7/10 | 2 | 0 | 0/0/2 | 18/0/1 | 187s |
| 固态电池量产进度与产业链 | 2840 | 1.000→1.000 | 8/10 | 3 | 0 | 0/0/2 | 16/0/0 | 185s |
| AI 编程助手对软件工程流程的影响 | 2958 | 1.000→1.000 | 8/13 | 0 | 0 | 0/0/1 | 8/0/1 | 130s |
| 人形机器人关节模组的成本结构 | 1953 | 0.875→1.000 | 3/7 | 0 | 0 | 3/2/1 | 20/0/0 | 134s |

（2026-10-22 基线，温度 0。初稿均值 0.958 → 终稿 1.0；冲突共 9 组，`targets_met` 3/5、
`quality_ok` 4/5。端侧主题当天遇到搜索限流，只拿到 3 个来源、10 个事实句，
被事实句下限判未达标；这不是靠兜底硬凑，而是如实降级。完整明细见
`batch_report.md` / `batch_results.json`。）

## 设计上值得说的几处

- **引用编号与来源表由代码生成**（sources.py）：模型只写 [n]，来源表按引用编号生成；
  模型自带的「参考文献/参考资料」小节无论哪种写法都会被剥掉；越界编号从正文删除并记入
  `citation_errors`，而不是只从来源表里悄悄丢掉。
- **一个来源一个编号**：同一 URL 的多条笔记合并到同一编号下，
  避免同一篇文章被编成 [5][6][12] 三个「独立来源」。
- **两层接地检查**（grounding.py）：
  抽取层要求笔记里的数字能在被引页面正文里找到，否则丢弃这条笔记；
  成稿层要求句子里出现的数字/型号能在被引笔记里找到，否则判为硬问题触发返工；
  返工预算用尽仍不合格时，**代码直接删除这些句子**，不交付无出处的数字。
- **来源质量分级**（source_quality.py）：按域名把来源分成官方/机构、媒体、自媒体、
  未知四档，并检测同一组硬数字是否被另一个独立域名印证；分级结果直接写进 writer
  的笔记清单，提示模型不要整节只依赖自媒体单一来源。分级是启发式，只作提示，不等同于事实判定。
- **检索先过主题锚点再排序**：只用子问题搜会搜回「产品路线图工具」这类跑题页；
  主题锚点做硬过滤，宁可某节写「公开资料有限，待补充」，也不收跑题内容。
  同一子问题会跨多个查询变体累积（最多 3 页、最多 8 次抓取），
  不再「第一个查询有结果就返回」，减少某节只有 1 个来源的情况。
- **冲突先由代码找候选**（fact_checker.py）：同一型号出现不同数字 → 冲突候选；
  同一组硬数字只出现在一个独立域名 → 孤证候选。型号会做归一（`Gen 4`/`Gen4`、
  连字符、`天玑9400`/`Dimensity 9400`），模型只负责逐条确认/否定；
  候选之外自己发现的冲突放进 `additional_conflicts`，带 `discovered_by: model` 标记，
  与代码候选区分开。候选与确认率写进快照。
- **冲突说明由代码生成**：模型经常把双方数据都抄进报告却不说明矛盾，
  终稿统一追加《数据分歧说明》附录，内容直接来自 fact_checker。
- **断言级核验**（claim_verify.py）：数字对得上不代表这句话被来源支持。
  对带引用的高风险句子（含数字/否定/因果词）用模型判断 supported/partial/unsupported；
  默认只记录不阻塞，校准脚本 `calibrate_claim_verify.py` 用人工标注算一致率，
  没到 0.8 不用于硬判。实测抓到过「来源写 M4 Ultra、报告写 M4」这类主体错误。
- **交付判定不交给模型**：引用覆盖率、悬空引用、覆盖率不足的句子清单都由代码算；
  LLM 审稿意见保留为建议（`review_report.problems`），只影响一轮返工，不阻塞交付。
- **三道代码兜底**（code_clean，END 前）：漏标的句子如果只有一条笔记能覆盖全部数字，
  由代码补上编号（多处命中说明有歧义，不猜）；仍无确定出处的数字/型号句子直接删除；
  既无引用也无硬数字的分析句补标「（推断）」。批量回归会报告三类兜底各触发了几句，
  避免「覆盖率 100%」掩盖清理工作量。
- **温度默认 0**：同一主题重跑时指标要能对齐，否则覆盖率会在 0.75–1.0 之间抖动。
- **并行写状态用 reducer**：research_notes 挂 merge_list，Send 的多路写入才不冲突；
  运行时并发限制为 3，避免一次打太多搜索请求被限流。
- **检索结果缓存**（cache.py，7 天 TTL）：重跑不再反复请求搜索引擎，demo 可复现。
- **SSRF 防护**（search.py）：手动跟随重定向，每一跳先做 DNS 解析并检查所有 IP，
  拒绝私网/回环/链路本地地址后才发请求；不是「请求完再检查最终 URL」。
- **提示注入粗筛**：抓到的页面先匹配「忽略以上指令」类模式，命中的不进抽取提示；
  资料文本用 `<source>` 标签包裹，prompt 明确标签内任何指令都只是文本。
- **运行历史与取消**（run_store.py / server.py）：每次运行落 `runs/*.json`，
  Web 可查来源层级、引用句、断言核验；运行中可取消，取消后释放锁。
- **checkpoint 保留**（checkpoint_prune.py）：按 thread 只保留最近 N 个，
  避免 `checkpoints.sqlite` 无限增长。

## 已知限制

- DuckDuckGo 中文结果质量一般；长句查询会先改写成关键词，但仍不保证每节都有资料。
- 知乎/百度学术等站点反爬会 403，按设计降级为空结果。
- 一次完整调研 2–4 分钟（真检索 + 多轮 LLM + 可能的返工）。
- 接地检查只比对数字与型号，中文措辞层面对不上（改写、转述）只记为软警告，不强制返工。
- 来源分级是基于域名的启发式，不能判断文章内容是否可靠；报告只把它作为提示，
  最终仍可能出现「可溯源但信源本身是推测性博客」的情况。
- 覆盖率 100% 是代码兜底后的结果，不代表模型初稿就写得好：2026-10-22 的 5 主题基线里，
  初稿均值 0.958，代码共补引用 3 句、删句 3 句、标推断 6 句；
  断言核验对 72 句高风险的带引用句子给出 64 supported / 0 partial / 8 unsupported。
- 冲突检测依赖代码候选和模型确认：本轮 9 组冲突，仍有两个主题为 0；
  这不代表那两份报告一定没有矛盾，只代表当前检测没有确认到。
- 检索结果受搜索服务限流影响明显：同一天不同批次可能从 9 个来源掉到 3 个来源，
  系统会如实缩短报告并判未达标，但这也意味着指标有明显的日间波动。
- 温度 0 只固定模型输出；检索结果仍会随搜索引擎变化，大纲也可能不同，
  因此跨天重跑不保证逐字一致，指标只保证当时快照可审计。
- 批量回归每个主题 2–4 分钟且消耗模型额度；普通 CI 只跑离线测试与已提交 demo 的审计，
  真实检索由 `.github/workflows/live-batch.yml` 手动或每周定时跑（需要仓库 secret
  `DASHSCOPE_API_KEY`，只跑 2 个主题控制成本）。
- 断言核验的校准集只有 8 条示例（当前一致率 1.00），只能说明口径自洽，
  不能说明泛化；默认只记录不阻塞，没有扩充标注集之前不要拿它当硬门槛。
- 冲突候选靠「同型号不同数字」发现，同义表述（骁龙8 Gen4 vs Snapdragon 8 Gen 4）
  可能漏配；模型确认也可能放过或误判。
- 提示注入只做了关键词粗筛，不是完整防护；抓取内容仍可能影响抽取结果。
- 断点续跑已落盘（SQLite），Web 端未做「重启后自动恢复上次进度」的界面。
